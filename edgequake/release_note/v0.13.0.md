# EdgeQuake v0.13.0 — Retrieval-only mode, full chunk content & working `top_k`

**Release date:** 2026-06-29
**Previous release:** v0.12.11

This release makes EdgeQuake usable as a pure **retrieval engine** for external
agents: ask the workspace a question and get the relevant **chunks directly**,
with their **full content**, and a **`top_k` that actually controls how many**
chunks come back — no LLM answer required.

---

## ✨ Highlights

### 1. Retrieval-only mode (`retrieval_only` / `context_only`)
Return the retrieved context **without** invoking the LLM to generate an answer.
The response carries the chunks/entities/relationships; your own agent (or
another platform) formulates the final answer.

- **Zero LLM cost**: no answer generation, no token usage, no LLM-based
  conversation-title generation.
- Works on **both** the streaming and non-streaming chat endpoints, and is
  already available on the dedicated `/query` endpoint via `context_only`.

| Endpoint | Flag | Behaviour |
|---|---|---|
| `POST /api/v1/chat/completions` | `"retrieval_only": true` | `content: ""`, chunks in `sources[]` |
| `POST /api/v1/chat/completions/stream` | `"retrieval_only": true` | emits a `context` SSE event with sources, then `done` — **no `token` events** |
| `POST /api/v1/query` | `"context_only": true` | `answer: ""`, chunks in `sources[]` (no conversation records created — recommended for external agents) |

### 2. Full source content (`content` field)
`SourceReference` now carries a **`content`** field with the **complete** chunk
text — not just the ~200-char `snippet` preview. Previously callers only received
a truncated fragment cut mid-sentence, which made the context look sparse and
made downstream agents produce shallow answers.

- **Chunks always carry full `content`** (both normal LLM-answer responses and
  retrieval-only), so an external agent never receives a truncated chunk. Chunks
  routinely run to ~2,500–3,000+ characters each.
- `snippet` remains the short preview for compact citation display.
- Entity full descriptions are included in retrieval-only mode.

### 2b. Source-type filter (`source_types`)
Restrict the returned `sources` (and the streaming `context` event) to specific
types — e.g. `"source_types": ["chunk"]` returns chunks only, dropping the
60+ entities and 60+ relationships that otherwise bloat the event. The LLM answer
is unaffected (it still uses the full graph context). The Web UI now requests
**chunks only** by default, shrinking the `context` event from ~128 sources to
just the chunks.

> **Getting the source file:** every chunk includes `document_id` (+ `file_path`
> and `start_line`/`end_line`). Fetch the full original document via
> `GET /api/v1/documents/{document_id}`.

```jsonc
{
  "source_type": "chunk",
  "id": "…-chunk-5",
  "score": 1.83,
  "snippet": "preview, ~200 chars…",   // unchanged
  "content": "…full ~3086-char chunk text…"  // NEW, retrieval-only
}
```

### 3. Assembled prompt passthrough (`include_prompt`)
Retrieval-only callers can request the **exact, fully-assembled prompt the LLM
would receive** — role + instructions + formatted knowledge-graph context +
full document chunks + the query — in a single `prompt` field, with **zero LLM
cost**. An external agent can inject this verbatim instead of re-assembling the
context itself.

- `POST /api/v1/chat/completions` with `"retrieval_only": true, "include_prompt": true`
  → `prompt` field (~30 K chars for a rich query), `content` empty.
- Streaming: the assembled prompt is delivered in the `context` SSE event's
  `prompt` field.
- Backed by the engine's existing `prompt_only` mode (also available directly on
  `POST /api/v1/query` with `"prompt_only": true`, where it is returned in `answer`).

> Why this matters: the LLM never reads the 200-char `snippet`. It reads the full
> context assembled by `to_context_string()` (full chunk text + every entity +
> every relationship). `include_prompt` hands your agent that exact material.

### 4. `top_k` is now honoured
The request `top_k` (chat) / `max_results` (`/query`) previously had **no effect** —
it was never threaded into the retrieval engine, so the number of chunks was fixed
by an internal config (`chunk_top_k = 20`). It now **caps the retrieved chunks** to
the requested value.

- Chunks are score-sorted, so capping keeps the **top-K most relevant**.
- `top_k = 1` returns the single best chunk; `top_k = 5` returns the best five.
- The effective ceiling is the engine's configured `max_chunks` (chunks are
  retrieved up to that depth, then capped to `top_k`).
- Entities and relationships are graph context and remain governed by the engine
  configuration (not affected by `top_k`).

## 🖥️ Frontend (Web UI)

- New **“Retrieval only (raw chunks)”** toggle in the query settings panel
  (*Paramètres de requête → Response Mode*), beside the Streaming toggle.
- When enabled, the UI renders the retrieved source citations instead of an
  LLM-generated answer bubble. Source context is now attached as soon as the
  `context` event arrives (so chunks render even when no answer tokens follow).
- **Readable chunks:** source passages now use the **full** `content` (not the
  200-char preview) and each passage is **expandable inline** (“Voir tout” /
  “Réduire”) with a scrollable full-text view, a character count, and the
  `L<start>–<end>` line locator. A separate icon still deep-links the passage in
  the document viewer.
- The setting persists with the other query settings.

## 📡 API examples

Retrieval-only, streaming, capped to the 3 most relevant chunks:

```bash
curl -N 'http://localhost:8049/api/v1/chat/completions/stream' \
  -H 'content-type: application/json' \
  -H 'x-tenant-id: <tenant>' -H 'x-user-id: <user>' -H 'x-workspace-id: <workspace>' \
  --data-raw '{"message":"c'\''est quoi le produit odyssey 2026 altaroc ?",
               "mode":"hybrid","top_k":3,"stream":true,"retrieval_only":true,"language":"fr"}'
# → conversation, context (3 chunks with full `content`), done. No token events.
```

Clean retrieval for an external agent (no conversation persistence):

```bash
curl 'http://localhost:8049/api/v1/query' \
  -H 'content-type: application/json' \
  -H 'x-tenant-id: <tenant>' -H 'x-user-id: <user>' -H 'x-workspace-id: <workspace>' \
  --data-raw '{"query":"…","mode":"hybrid","context_only":true,"max_results":5}'
# → { "answer": "", "sources": [ { …, "content": "<full chunk>" }, … ] }
```

## 🔄 Compatibility & migration

- **Backward compatible.** All new request fields default to off
  (`retrieval_only`/`context_only` = `false`) and `top_k` is optional. Existing
  clients are unaffected.
- The new `content` response field is omitted unless retrieval-only is requested.
- No database migrations.

---

## 🛠️ Notes / limitations

- Chunk ordering is by vector similarity and is **mode-independent**
  (`local`/`global`/`hybrid`/`naive` change the entity/relationship graph context,
  not the chunk ranking). For sharper ranking, reranking can be enabled in a
  follow-up.
- `top_k` is an upper bound capped at the engine's `max_chunks`; raising the
  effective retrieval depth above that default is a separate change.
