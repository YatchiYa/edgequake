# EdgeQuake v0.13.0 — Retrieval engine for external agents

**Release date:** 2026-06-29
**Previous release:** v0.12.11

This release turns EdgeQuake into a first-class **retrieval engine** you can drive
from another platform: query a workspace and get back the **relevant chunks**,
**in full**, with precise control over **how many**, **which source types**, and
optionally the **exact prompt** the LLM would have used — with **zero LLM cost**
when you don't want a generated answer.

It also fixes a class of confusion where the retrieved sources *looked* poor
(truncated 200-char previews) even though the LLM was answering from the full
context.

## 1. Retrieval-only mode

Return the retrieved context **without** running the LLM to generate an answer.
Your own agent (on another platform) writes the final answer from the raw context.

- **Zero LLM cost**: no answer generation, no token usage, and no LLM-based
  conversation-title generation.
- Available on **both** chat endpoints, plus the dedicated `/query` endpoint.

| Endpoint | Flag | Behaviour |
|---|---|---|
| `POST /api/v1/chat/completions` | `"retrieval_only": true` | `content: ""`, chunks in `sources[]` |
| `POST /api/v1/chat/completions/stream` | `"retrieval_only": true` | emits a `context` SSE event with sources, then `done` — **no `token` events** |
| `POST /api/v1/query` | `"context_only": true` | `answer: ""`, chunks in `sources[]`; **creates no conversation records** — recommended for external agents |

## 2. Full chunk content (always)

`SourceReference` gained a **`content`** field carrying the **complete chunk text**
(not the ~200-char `snippet` preview). Crucially, **chunks always include their
full `content`** now — in normal LLM-answer responses *and* in retrieval-only —
so a downstream agent never receives a truncated chunk.

- `snippet` stays as the short preview for compact citation display.
- Full entity descriptions are additionally included in retrieval-only mode.
- Typical chunk content runs ~2,400–3,100 characters; a full document's worth of
  chunks is ~22,000 characters of usable context.

```jsonc
{
  "source_type": "chunk",
  "id": "…-chunk-5",
  "score": 1.83,
  "snippet": "preview, ~200 chars…",          // short preview (unchanged)
  "content": "…full ~3086-char chunk text…",   // NEW — always present for chunks
  "document_id": "cdfd2960-…",
  "file_path": "altaroc_produits.md",
  "start_line": 278, "end_line": 337
}
```

## 3. Source-type filtering (chunks-only by default)

Returned `sources` (and the streaming `context` event) are now restricted to
**chunks only by default** — the 60+ entities and 60+ relationships that made the
event huge (~128 sources) are excluded unless explicitly requested.

**Two levers:**
- **Per request** — `"source_types": ["chunk"]` (or `["chunk","entity"]`, etc.).
  An explicit value always wins.
- **Server default** — env var **`EDGEQUAKE_DEFAULT_SOURCE_TYPES`** (applied when a
  request omits `source_types`):
  - unset → **`chunk`** (chunks only) — the new default
  - `all` (or empty) → every type (chunks + entities + relationships)
  - `chunk,entity,relationship` → an explicit subset

- The **LLM answer is unaffected** — it always uses the full knowledge-graph context.
- The Web UI omits `source_types`, so it follows the server default (chunks-only),
  and `EDGEQUAKE_DEFAULT_SOURCE_TYPES=all` re-enables the Knowledge-Graph view in
  the citations panel without a frontend rebuild.

## 4. Working `top_k`

The request `top_k` (chat) / `max_results` (`/query`) previously had **no effect** —
it was never threaded into the retrieval engine, so the chunk count was fixed by an
internal config (`chunk_top_k = 20`). It now **caps the retrieved chunks**.

- Chunks are score-sorted, so the cap keeps the **top-K most relevant**.
- `top_k = 1` → single best chunk; `top_k = 5` → best five.
- Upper bound is the engine's configured `max_chunks` (retrieved to that depth,
  then capped to `top_k`).
- Entities/relationships are graph context, governed separately by the engine config.

## 5. Assembled-prompt passthrough

New request field **`include_prompt`** returns the **exact, fully-assembled prompt
the LLM would receive** — role + instructions + formatted knowledge-graph context
+ full document chunks + the query — in a single field, with **zero LLM cost**.

- `POST /api/v1/chat/completions` with `"retrieval_only": true, "include_prompt": true`
  → `prompt` field (~30 K chars for a rich query); `content` empty.
- Streaming → delivered in the `context` SSE event's `prompt` field.
- Backed by the engine's existing `prompt_only` mode (also directly available on
  `POST /api/v1/query` with `"prompt_only": true`, returned in `answer`).

Use this when you want your agent to produce an answer **as exhaustive as
EdgeQuake's own LLM** — inject the prompt verbatim.

## 6. Getting the source file

Every chunk carries `document_id`, `file_path`, and `start_line`/`end_line`. To
fetch the **full original document**:

```
GET /api/v1/documents/{document_id}
```

returns the document with its complete content. Use `start_line`/`end_line` to
locate the chunk within it.

## 7. Frontend (Web UI)

- New **“Retrieval only (raw chunks)”** toggle in the query settings panel
  (*Paramètres de requête → Response Mode*), beside Streaming.
- **Readable chunks:** source passages now use the **full** `content` (not the
  200-char preview) and each passage is **expandable inline** (“Voir tout” /
  “Réduire”) with a scrollable full-text view, a **character count**, and the
  `L<start>–<end>` **line locator**. A separate icon still deep-links the passage
  into the document viewer.
- The `context` source list is fetched **chunks-only** by default (less noise).
- Source context attaches to the message as soon as the `context` event arrives,
  so chunks render even when no answer tokens follow (retrieval-only).

> Note: chunks-only display means the citations’ Knowledge-Graph (entities /
> relationships) view is empty by default. It can be re-enabled by widening the
> UI’s `source_types`.

## 8. Why the LLM answer was richer than the sources

A common confusion this release resolves: the generated answer was detailed, yet
the listed sources looked sparse. The reason — **the LLM never reads the
`snippet`**. It reads `QueryContext::to_context_string()`, which concatenates the
**full** chunk text + every entity (with description) + every relationship
(~22 K–30 K chars). The `snippet` was only a display preview.

With this release, retrieval-only callers receive that same full material
(`content` on every chunk; optionally the entire assembled `prompt`), so an
external agent can match the LLM's depth.

## 9. API reference & examples

New `ChatCompletionRequest` fields (all optional, default off):

| Field | Type | Meaning |
|---|---|---|
| `retrieval_only` | bool | retrieve, don't generate (zero LLM) |
| `include_prompt` | bool | also return the exact assembled prompt |
| `source_types` | string[] | restrict surfaced sources (e.g. `["chunk"]`); omit to use the `EDGEQUAKE_DEFAULT_SOURCE_TYPES` server default (`chunk`) |
| `top_k` | number | cap the number of chunks returned |

New response fields: `prompt` (assembled prompt, when requested); `SourceReference.content`
(full chunk text).

**Streaming, chunks-only, top 3, with the assembled prompt:**
```bash
curl -N 'http://localhost:8049/api/v1/chat/completions/stream' \
  -H 'content-type: application/json' \
  -H 'x-tenant-id: <tenant>' -H 'x-user-id: <user>' -H 'x-workspace-id: <workspace>' \
  --data-raw '{"message":"c'\''est quoi le produit odyssey 2026 altaroc ?",
               "mode":"hybrid","top_k":3,"stream":true,
               "retrieval_only":true,"include_prompt":true,
               "source_types":["chunk"],"language":"fr"}'
# → conversation, context (3 full-content chunks + prompt), done. No token events.
```

**Clean retrieval for an external agent (no conversation persistence):**
```bash
curl 'http://localhost:8049/api/v1/query' \
  -H 'content-type: application/json' \
  -H 'x-tenant-id: <tenant>' -H 'x-user-id: <user>' -H 'x-workspace-id: <workspace>' \
  --data-raw '{"query":"…","mode":"hybrid","context_only":true,"max_results":5}'
# → { "answer": "", "sources": [ { …, "content": "<full chunk>" }, … ] }
```

## 10. Compatibility & migration

- **Backward compatible.** All new request fields default to off; existing clients
  are unaffected.
- The `content` field is additive; `prompt` is omitted unless requested.
- No database migrations.
- Behavioural change worth noting: chunk `content` is now present on **normal**
  chat responses too (previously retrieval-only). This enlarges those payloads;
  pair with `source_types: ["chunk"]` to keep them lean.

## 11. Ops / deployment

- `docker-compose.yml`: `NEXT_PUBLIC_API_URL` is now configurable (was hardcoded);
  new `EDGEQUAKE_DEFAULT_SOURCE_TYPES` (default `chunk`) controls which source
  types are surfaced by default — set to `all` to include entities/relationships.
- `.env`: pinned ports — API `8049`, frontend `8048`, Postgres `5433`.
- Run:
  ```bash
  cd edgequake/docker
  docker compose --env-file ../.env up -d
  ```
  `--env-file ../.env` is required (compose interpolates `OPENAI_API_KEY`,
  `POSTGRES_PASSWORD`, `NEXT_PUBLIC_API_URL`, ports from it). If you change the API
  port, **rebuild the frontend** (`NEXT_PUBLIC_API_URL` is baked at build time).
- Versions bumped to **0.13.0** (workspace crates + `edgequake_webui`).
